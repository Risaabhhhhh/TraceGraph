# ChainGuard Blockchain Integration Report

## 1. Executive Summary & Architecture

ChainGuard bridges probabilistic machine learning risk detection with verifiable on-chain registries on the Ethereum Virtual Machine (EVM). The architecture is structured into two core contracts:

1. **`ModelRegistry.sol`**:
   - Manages model artifact provenance, versioning (`v1.0.0`), documentation URIs (`ipfs://...`), and cryptographic identity (`bytes32 modelHash`).
   - Implements role-based access control (`MODEL_MANAGER_ROLE`) to activate or revoke approved models.
   
2. **`RiskRegistry.sol`**:
   - Implements an amortized, batch-oriented risk publishing pipeline (`createBatch` $\to$ `publishScores`).
   - Every published batch cryptographically links to an **active model** in `ModelRegistry` (`modelHash`) and an immutable **input transaction snapshot** (`snapshotHash`).
   - Scores are stored as 16-bit unsigned integers representing basis points ($0$ to $10,000$, equivalent to $0.00\%$ to $100.00\%$ illicit probability).

```
┌─────────────────────────────────┐
│     Trained Model Artifact      │
│  (XGBoost 165 Feat, Seed 42)   │
└────────────────┬────────────────┘
                 │ SHA-256 Hash
                 ▼
┌─────────────────────────────────┐       Validates Active Model
│       ModelRegistry.sol         │ ◄──────────────────────────────┐
│  - modelHash: 0x69082f2...      │                                │
│  - version: "v1.0.0"            │                                │
│  - active: true                 │                                │
└─────────────────────────────────┘                                │
                                                                   │
┌─────────────────────────────────┐       createBatch(modelHash)   │
│       RiskRegistry.sol          ├────────────────────────────────┘
│  - nextBatchId: 0               │
│  - batches[batchId]:            │
│      * modelHash                │
│      * snapshotHash             │
│      * count / timestamp        │
│  - scores[address]:             │ ◄── publishScores(batchId, addrs, scores)
│      * score: 8540 (85.40%)     │
└─────────────────────────────────┘
```

## 2. Gas Consumption & Scalability Analysis

Risk score publishing in public blockchain environments is gas-sensitive. By separating batch header initialization (`createBatch`) from bulk score writing (`publishScores`), ChainGuard amortizes base transaction overhead across hundreds of scored addresses.

The gas benchmarks below were measured directly on the local Hardhat EVM environment using the Solidity 0.8.20 compiler with 200 optimizer runs:

| Batch Size | Transaction Gas Used | Gas Cost Per Address | Relative Efficiency vs. Single |
|:---:|:---:|:---:|:---:|
| **1 Address** | 115,301 gas | 115,301 gas/addr | Baseline (1.00x) |
| **10 Addresses** | 548,194 gas | 54,819 gas/addr | **52.5% reduction** (2.10x faster) |
| **50 Addresses** | 2,548,128 gas | 50,963 gas/addr | **55.8% reduction** (2.26x faster) |

### Key Gas Optimization Mechanisms:
- **Basis Points (uint16)**: Compacting risk scores to `uint16` ($0..10000$) preserves precision to 2 decimal places while allowing compact storage packing.
- **Batched Calldata Arrays**: Passing `address[]` and `uint16[]` calldata arrays enables tight loop execution with `unchecked` iterator increments.
- **Single Model & Snapshot Verification**: The model active status and snapshot lineage are verified once per batch rather than per individual score record.

## 3. Core Principle: "Provenance is Not Truth"

A central tenet of ChainGuard's system design is the explicit distinction between **cryptographic provenance** and **empirical accuracy**:

> **"Verified origin, not verified accuracy."**

1. **What On-Chain Verification Guarantees**:
   - **Tamper Evidence**: Once recorded on-chain, nobody can alter the risk score assigned to an address without emitting an event and updating the batch ID.
   - **Auditable Lineage**: Any decentralized application, compliance officer, or protocol can verify that score $S$ for address $A$ was generated by model $M$ (matching SHA-256 binary hash `0x6908...`) operating on data snapshot $D$ (matching SHA-256 hash `0xa1b2...`).
   - **Model Authorization**: Scores cannot be published using unapproved, deprecated, or revoked model hashes.

2. **What On-Chain Verification Does NOT Guarantee**:
   - **Infallible Truth**: Machine learning models produce probabilistic estimates. A score of $85.40\%$ indicates that the model detected behavioral patterns similar to illicit transactions in the historical Elliptic dataset, not an absolute legal determination of guilt.
   - **Ground Truth Invariance**: As shown in ML Phase 2/3 drift experiments, macro structural changes (e.g. darknet marketplace takedowns) can shift underlying distributions. Provenance guarantees which model ran, not that the model never makes false positives.

## 4. System Limitations & Scope

1. **Dataset & Demo EVM Address Mapping**:
   - The primary benchmark dataset (Elliptic) comprises Bitcoin transaction hashes. In this implementation, test-window transaction nodes (Steps 40–49) are mapped deterministically to synthetic EVM demo addresses (`0x...`) for interaction with standard Ethereum tooling.
   - This implementation serves as an end-to-end **pipeline demonstration** of ML provenance and batch publishing, not a real-time live Ethereum detection system. In a production EVM deployment, raw ERC-20 / ETH transfer graphs and account-level features would replace the Elliptic transaction graph.

2. **Network Deployment & Scope**:
   - The contracts were deployed and fully tested on a **local Hardhat network** (`http://127.0.0.1:8545`, Chain ID 31337).
   - A Sepolia testnet configuration is included in `contracts/hardhat.config.ts`, but live Sepolia broadcast was cut per the project cut list.

3. **DApp Architecture**:
   - The user interface is built as a lightweight, dependency-free **Vanilla HTML/CSS/JavaScript single-page application** rather than a full Next.js/React framework. It performs direct read-only JSON-RPC queries to the blockchain and FastAPI backend without requiring wallet writes or user signatures.

4. **Interpretability & Retraining Scope**:
   - Feature attribution via SHAP and node/edge attribution via GNNExplainer were not executed in this fast pass.
   - Continuous retraining strategies (train-once vs. periodic vs. drift-triggered retraining schedules) were evaluated conceptually via the Rolling-Origin Experiment C analysis, but automated dynamic retraining orchestrators were omitted.
